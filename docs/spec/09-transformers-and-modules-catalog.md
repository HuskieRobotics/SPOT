# 09 — Transformers and Modules Catalog

## Transformer framework

- **TR-1** `class DataTransformer { constructor(name, execFunc); execute(dataset, outputPath, options) }`
  — `execute` simply calls `execFunc`. (The comment about making existing paths read-only is
  not implemented.)
- **TR-2** Transformer files live in `src/analysis/transformers/`. A file may contain one
  `__TMP__ … __/TMP__` block and one `__TEAM__ … __/TEAM__` block, each holding exactly one
  `new DataTransformer("<fileName>", fn)` expression **without** a trailing semicolon. The
  bundle route wraps them as `{ tmp: { name: <expr>, … }, team: { … } }` inside an async
  `getTransformers()` that first fetches `match-scouting.json` and computes `actionIds`
  (unique button ids across all layers, first-appearance order). `getPath`, `setPath`, and
  `matchScoutingConfig` are available to transformer code as globals from the template scope.
- **TR-3** Helper semantics: `getPath(obj, "a.b.c", ifnone)` throws if the path is missing and
  no default is given; `setPath` creates intermediate objects.
- **TR-4** `tmp` transformers iterate `dataset.tmps`; `team` transformers iterate
  `Object.entries(dataset.teams)` and select `dataset.tmps.filter(t => t.robotNumber == team)`.

### v6 engine (`src/analysis/engine`, #310)

- **TR-5** The dataset is `{ tmps, teams }`. Each tmp is the stored performance projected to its
  public fields (`_id`, `eventId`, `matchNumber`, `team`, `source`, `clientVersion`,
  `submittedAt`, `coverage`, `superseded`, `flag`, `notes`, `tags`, `actions`): no scouter id and
  no `matchKey`, which embeds it (SEC-8). Actions are as stored, a button id plus the period
  (CS-16). `teams` has one object per team key (DM-1a), compared with `===`, never `==`.
- **TR-6** Performances are ordered by `submittedAt`, then `_id`. On the real exports this is the
  legacy order (timestamp, then `matchId`).
- **TR-7** Stored fields are frozen and cannot be replaced or deleted; entries only add outputs.
  An in-place change such as v5's `finalActionOccurrence` reversal (F-3) throws.
- **TR-8** `getPath` keeps TR-3, with two changes: a `null` part-way along a path counts as
  missing (v5 threw even when given a default), and a `null` leaf is returned as `null`.
  `setPath` refuses to write through an existing non-object value (v5 silently replaced a falsy
  one with `{}` and ignored a truthy one).
- **TR-9** Transformers are registered by entry type and name, in one of three shapes: per
  performance (`tmp`), per team (`team`, given the team's performances in dataset order), or
  over the whole dataset (`removeDuplicates`). Each declares a JSON Schema for its options
  (ADR 0005); built-ins reference `$defs/options` in the pipeline schema.
- **TR-10** Before running, every entry is checked; an unknown transformer (with a "did you mean"
  suggestion) or invalid options is reported and only that entry is skipped. While running, a
  failure is reported per entry with the count of failing performances or teams and the first
  one, and everything else still runs. Every written value is normalized so NaN, ±Infinity and
  undefined become `null` (DM-1b).
- **TR-11** Arithmetic inputs (decided 2026-11-20, #312): a missing path counts as 0 (1 for a
  `multiply` factor), as in v5; a `null` input ("No Data") makes the result `null`, as v5's NaN
  did; any other non-number is an error naming the path (v5 concatenated strings or produced NaN).
  A value that should rank a team last is set explicitly where it is produced (`ratio.divByZero`,
  F-24), not inferred from missing data.

**[A-38]** The `cycle` pairing semantics above are confirmed as intended. **[A-39]**
**Decided 2026-11-20:** `sumAverage` takes explicit `countPaths`; v6 has no name-convention
inference, because the composite-id names it relied on are gone (CS-16). The v1 → v2 converter
writes out the paths v5 would have inferred, so converted configurations keep their meaning.
This follows the configuration principle that a typical game is easy to encode and an unusual
one is possible with more explicit configuration.

Transformer authoring rules (from CONTRIBUTING and TRANSFORMERS_README): document options with
JSDoc, keep one transformer per type per file, never delete or modify existing dataset paths,
handle divide-by-zero and missing data, avoid game terminology, and put any code outside the
`new DataTransformer(...)` expression into the template file rather than the transformer file.

## Module framework

- **MO-1** A module is a class with `constructor(moduleConfig)` creating `this.container`
  (`div.container.<kind>`), `formatData(teams: string[], dataset) → data` (may be async), and
  `setData(data)` (may be async). `moduleConfig` is the entry from `analysis-modules.json`.
- **MO-2** Modules are discovered from `src/analysis/modules/<Name>/index.js` and
  `style.css`; the class name must equal the folder name.
- **MO-3** Common option conventions: `path` (team path), `aggrMethod: "sum"` (else average
  across the given teams), `multiplier`, `addend`, `decimals`, `unit`, `hideIfValue`,
  `sort` (1 = higher is better, -1 = lower is better, 0/undefined = no rank).
- **MO-4** Rank badges: when `sort` is set and a single team is displayed, the team's rank
  among all teams with a valid value is computed; CSS classes `top5` (≤ 5 %), `top25`, `top50`,
  else `top100`.
- **MO-5** Plotly modules call `getCssVar` for theme colors, use font Cairo, title size 32,
  `responsive: true`, and remove the zoom/pan mode-bar buttons.
