# 09 — Transformers and Modules Catalog

## Transformer framework

- **TR-1** `class DataTransformer { constructor(name, execFunc); execute(dataset, outputPath, options) }`
  — `execute` simply calls `execFunc`. (The comment about making existing paths read-only is
  not implemented.) **v5.** v6 replaces it with TR-9, and makes stored fields read-only (TR-7).
- **TR-2** Transformer files live in `src/analysis/transformers/`. A file may contain one
  `__TMP__ … __/TMP__` block and one `__TEAM__ … __/TEAM__` block, each holding exactly one
  `new DataTransformer("<fileName>", fn)` expression **without** a trailing semicolon. The
  bundle route wraps them as `{ tmp: { name: <expr>, … }, team: { … } }` inside an async
  `getTransformers()` that first fetches `match-scouting.json` and computes `actionIds`
  (unique button ids across all layers, first-appearance order). `getPath`, `setPath`, and
  `matchScoutingConfig` are available to transformer code as globals from the template scope.
  **v5.** In v6 a built-in is a TypeScript module listed in `src/analysis/transformers/index.ts`
  and an extension one listed in `src/analysis/extensions/index.ts` (TR-14); `getPath` and
  `setPath` are imports, and the configuration reaches a transformer in its run context.
- **TR-3** Helper semantics: `getPath(obj, "a.b.c", ifnone)` throws if the path is missing and
  no default is given; `setPath` creates intermediate objects.
- **TR-4** `tmp` transformers iterate `dataset.tmps`; `team` transformers iterate
  `Object.entries(dataset.teams)` and select `dataset.tmps.filter(t => t.robotNumber == team)`.
  **v5.** v6 keeps the iteration with team keys compared by `===` (TR-5, TR-9).

### v6 engine (`src/analysis/engine`, #310)

- **TR-5** The dataset is `{ tmps, teams }`. Each tmp is the stored performance projected to its
  public fields (`_id`, `eventId`, `matchNumber`, `team`, `source`, `clientVersion`,
  `submittedAt`, `coverage`, `superseded`, `flag`, `notes`, `tags`, `actions`): no scouter id and
  no `matchKey`, which embeds it (SEC-8). Actions are as stored, a button id plus the period
  (CS-16). `teams` has one object per team key (DM-1a), compared with `===`, never `==`.
  A superseded performance is left out (decided 2026-11-20, #314): a re-scout replaced it
  (RT-14a) or it lost to the replacement scouter's record (RT-35), so no pipeline can count a
  match twice. This replaces v5's `removeDuplicates` entry, which a pipeline could leave out
  (the 2025 v4.2.0 pipeline counted its 3 re-scouts twice). Flagged performances stay in, as in
  v5, and so do partial ones (a replacement who joined mid-match, RT-34, which RT-36 flags); the
  dashboard warns about them (AN-18a). `teams` is in team-key order (DM-1a), so team entries
  run, and write, in that order.
- **TR-6** Performances are ordered by `matchNumber`, then `submittedAt`, then `_id` (decided
  2026-11-20, #314), so a team's performances, and lists joined across them, read in match order.
  A match scouted later from video takes its place among the team's matches. v5 used submission
  order, except that a re-scout took the place of the first scout; on the real exports the two
  orders differ only for 2026's three video-scouted matches and its one re-scout.
- **TR-7** Stored fields are frozen and cannot be replaced or deleted; entries only add outputs.
  An in-place change such as v5's `finalActionOccurrence` reversal (F-3) throws.
- **TR-8** `getPath` keeps TR-3, with two changes: a `null` part-way along a path counts as
  missing (v5 threw even when given a default), and a `null` leaf is returned as `null`.
  `setPath` refuses to write through an existing non-object value (v5 silently replaced a falsy
  one with `{}` and ignored a truthy one). `observePathReads(onRead, fn)` reports every path read
  while `fn` runs, with the value found, and `runPipeline` takes `beforeEntry` and `afterEntry`
  callbacks; config:check uses both to find a path no earlier entry writes, so extensions need
  not declare what they read (#317, docs/spec/20 §4 CC-9).
- **TR-9** Transformers are registered by entry type and name, in one of three shapes: per
  performance (`tmp`), per team (`team`, given the team's performances in dataset order), or
  over the whole dataset (no built-in uses it since `removeDuplicates` was retired; it remains
  for extensions). Each declares a JSON Schema for its options
  (ADR 0005); built-ins reference `$defs/options` in the pipeline schema. All analysis code (the
  engine, the built-ins, TBA enrichment and extensions) runs in the browser as well as in Node:
  it imports nothing from Node, reads no files and fetches nothing, so the dashboard, the CSV
  export and config:check run the same pipeline (D-5, ADR 0005). A test scans `src/analysis`
  for this.
- **TR-10** Before running, every entry is checked; an unknown transformer (with a "did you mean"
  suggestion) or invalid options is reported and only that entry is skipped. While running, a
  failure is reported per entry with the count of failing performances or teams and the first
  one, and everything else still runs. Every written value is normalized so NaN, ±Infinity and
  undefined become `null` (DM-1b).
- **TR-11** Arithmetic inputs (decided 2026-11-20, #312): a missing path counts as 0 (1 for a
  `multiply` factor), as in v5; a `null` input ("No Data") makes the result `null`, as v5's NaN
  did; any other non-number is an error naming the path (v5 concatenated strings or produced NaN).
  A value that should rank a team last is set explicitly where it is produced (`ratio.divByZero`,
  F-24), not inferred from missing data.
- **TR-12** Aggregation across a team's matches (decided 2026-11-20, #313): a per-match value
  that is null or missing is skipped, as in v5, because an unrated match has no rating and a
  match without a climb has no climb time (how often something happened is a separate count).
  When there is nothing at all to average, `average`, `averageTime` and `averageArray` write
  `ifNone` when it is configured, else `null`. As with `ratio.divByZero`, an explicit worst value
  (the full match time for a cycle time, say) ranks a team that never did something last
  instead of leaving it out as "No Data"; in 2025, 5 of 42 teams never completed a coral cycle.

- **TR-13** Action sequences (decided 2026-11-20, #314): `actionTime`, `actionTimeFilter`,
  `finalActionOccurrence`, `cycle`, `countHybrid` and `zoneActionRatingGroupings` match actions
  by button id and take the period filters `phases`, `segments` and `kinds` (docs/spec/20 §2.2).
  Transformers that look at one action at a time filter the actions first. Transformers that pair
  actions (`cycle`, `countHybrid`, `zoneActionRatingGroupings`) pair over the whole match first,
  then a filter keeps a pair whose first or last action is in the period, so a pair that crosses
  a boundary is kept by a filter for either period. Filtering first would break such pairs or
  match a start with an end from a later shift (F-26). A piece collected in auto and scored in
  teleop is one cycle with its full time, counted by an auto filter and by a teleop filter; a
  cycle entry without a filter lists each cycle once, so whole-match averages count nothing twice,
  but adding the cycle counts of two periods does (confirmed 2026-11-21, #320). Actions written into an output are
  copies, so the stored list is never changed (F-3). A value that cannot be found is `default`
  where the transformer has one, else `null`.
- **TR-14** Extension transformers (ADR 0005, #316; guide in `docs/extension-transformers.md`):
  an extension is a file in `src/analysis/extensions/` plus one line,
  `export { name } from "./name";`, in that folder's `index.ts`, kept alphabetical. Everything
  exported there is registered beside the built-ins. The rules are checked when the registry is
  created or by the unit tests, so a broken extension fails CI rather than an event:
  its name must be one a pipeline entry can use and must not be a built-in transformer's name,
  for either entry type, because the pipeline schema checks a built-in's options by name alone;
  its options schema must compile in Ajv strict mode and reject an option it does not know, as
  every built-in's does (CS-10); and, like all analysis code, it runs in the browser and fetches
  nothing (ADR 0005). The pipeline schema accepts any options for a name it does not know; the
  registry then checks them against the extension's schema, so `config:check` and the dashboard
  report a misspelled extension option exactly as they report a built-in one. A schema that does
  not compile is reported as a bug in the transformer's code, and only entries using it are
  skipped (TR-10). `src/analysis/extensions/examples/median.ts` is a worked example that is not
  registered.
- **TR-15** Pairing never queues (decided 2026-11-21, #320; replaces A-38). A later action pairs
  with the newest open action before it, so an action left without its partner (a drop nobody
  recorded, a mistaken tap, an unrated action) affects only itself and never shifts the pairs
  after it. v5 gave each start the first unused end after it, so one such start took the next
  start's end and every later cycle in the match moved by one (F-28). In `cycle`, at most
  `capacity` starts are open at once (default 1: a robot holding one game piece of that kind), an
  end or miss pairs with the newest open start recorded strictly earlier, a start beyond the
  capacity drops the oldest open one, and `unendedCount` counts the starts that never got an end.
  With a capacity above 1, which of several held pieces was scored first cannot be known; pairing
  with the newest keeps a leftover start from shifting later pairs, and the average cycle time is
  the same either way, because the same starts and ends are paired. In
  `zoneActionRatingGroupings`, a zone press says where the robot is until the next one.

**[A-38]** v5's `cycle` pairing (each start took the first unused end after it) was confirmed
on 2026-11-20 and **replaced on 2026-11-21** by TR-15, when the native 2026 configuration showed
what it does to a start without an end (F-28). **[A-39]**
**Decided 2026-11-20:** `sumAverage` takes explicit `countPaths`; v6 has no name-convention
inference, because the composite-id names it relied on are gone (CS-16). The v1 → v2 converter
writes out the paths v5 would have inferred, so converted configurations keep their meaning.
This follows the configuration principle that a typical game is easy to encode and an unusual
one is possible with more explicit configuration.

Transformer authoring rules (v5, from CONTRIBUTING and TRANSFORMERS_README): document options
with JSDoc, keep one transformer per type per file, never delete or modify existing dataset
paths, handle divide-by-zero and missing data, avoid game terminology, and put any code outside
the `new DataTransformer(...)` expression into the template file rather than the transformer
file. In v6 the engine enforces the dataset rule (TR-7), an options schema replaces the JSDoc
(TR-9), and `docs/extension-transformers.md` is the guide (TR-14).

## Module framework

- **MO-1** A module is a class with `constructor(moduleConfig)` creating `this.container`
  (`div.container.<kind>`), `formatData(teams: string[], dataset) → data` (may be async), and
  `setData(data)` (may be async). `moduleConfig` is the entry from `analysis-modules.json`.
- **MO-2** Modules are discovered from `src/analysis/modules/<Name>/index.js` and
  `style.css`; the class name must equal the folder name.
- **MO-3** Common option conventions: `path` (team path), `aggrMethod: "sum"` (else average
  across the given teams), `multiplier`, `addend`, `decimals`, `unit`, `hideIfValue`,
  `sort` (1 = higher is better, -1 = lower is better, 0/undefined = no rank).
- **MO-4** Rank badges: when `sort` is set and a single team is displayed, the team's rank
  among all teams with a valid value is computed; CSS classes `top5` (≤ 5 %), `top25`, `top50`,
  else `top100`.
- **MO-4a** (v6, #318) The value a module shows comes from `src/analysis/modules/display.ts`,
  which config:preview uses too: `value × multiplier + addend`, No Data when the value is
  missing, not a number, or equal to `hideIfValue`, then `decimals` and `unit`. A missing value
  is No Data, not 0 (F-27). Ties share a rank: two teams with the best value are both #1, and the
  next is #3. The rank is among every team at the event with a value.
- **MO-5** Plotly modules call `getCssVar` for theme colors, use font Cairo, title size 32,
  `responsive: true`, and remove the zoom/pan mode-bar buttons.

### v6: the text modules (#384)

The dashboard draws each module as a React component (`src/components/analysis/modules/`), from
values computed by plain functions (`src/analysis/modules/values.ts`, tested in `modules`).
Decided 2026-11-26:

- **MO-1, MO-2** A module is a component given its entry, the teams shown and the dataset. The
  registry in `src/components/analysis/modules/index.tsx` replaces v5's folder discovery; it lists
  every built-in module the schema names (a test checks), and extension modules join it in #391.
- **MO-3** Several teams (an alliance in Simulate Match, #389) are combined over the teams that
  have a value: summed with `aggrMethod: "sum"`, else averaged, and No Data when none has. v5
  counted a missing value as 0, pulling an alliance's average down (F-27).
- **MO-4, MO-4a** A rank badge shows when `sort` is set and one team is shown, among every team at
  the event with a value; ties share a rank. Its colour keeps v5's bands and rounding: the top 5 %
  in the accent colour, 25 % green, 50 % orange.
- **Grid** Each cell is summed over the teams, on its colour with an alpha from 30 at `min` to 255
  at `max`, rounded down as in v5. The alpha stays between 30 and 255, and `min` and `max` default
  to 0 and the largest cell's value: v5's colour broke below `min` or without them.
- **SingleDisplay** is never ranked, as in v5. Its `percentChanceOfWinning` compares two
  alliances, so it is drawn by Simulate Match (#389).
- **F-18** Nothing a module computes changes the teams or the dataset it is given.
